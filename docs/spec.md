# Real-Time Personalization on Databricks — Solution Spec

**Status:** Draft v0.3 — all major decisions confirmed; workspace constraints resolved (see decisions.md)
**Target segment:** Digital Native Business (DNB)
**Scenario (confirmed):** Online marketplace / e-commerce retailer
**Data source (confirmed):** Synthetic, streaming
**Intelligence layer (confirmed):** Two-stage recommender + Vector Search cold start + LLM explanations + merchandiser agent
**App framework (confirmed):** React (Vite + TypeScript) frontend + FastAPI backend

**Workspace (resolved):** FE VM workspace (AWS us-east-1), serverless jobs/pipelines/SQL, Lakebase Autoscaling, Vector Search, Claude + GTE Foundation Models available. Catalog `fevm_catalog_ra_test`.

---

## 1. Business Challenge

Digital-native commerce companies acquire users through paid channels and lose most of them in the first session. The default experience is one-size-fits-all: the same homepage, the same product rails, the same offers for a first-time visitor and a loyal repeat buyer. Consequences:

- Low session-to-purchase conversion and high bounce on landing pages
- Cold-start users (no history) get nothing better than "trending"
- Marketing/merchandising teams can't see *why* a user got a recommendation or whether it worked, so they can't iterate
- Personalization logic lives in app-team code, disconnected from the analytics data the business trusts

**Problem statement:** Deliver the right product recommendation to every user within ~100 ms of a page view, using the freshest signals available (what they just clicked), with full governance, explainability, and a business-facing feedback loop — all on one platform instead of a stitched-together ML stack + separate serving database + separate BI tool.

| Persona | Need |
|---|---|
| Shopper (end user) | Relevant products, fast |
| Merchandising manager | Understand recommendation performance by category/segment; ask ad-hoc questions in plain English |
| Data/ML engineer | One pipeline from raw events to served recommendations; lineage, monitoring, reproducibility |
| Executive | Business impact: lift in conversion, AOV, retention |

## 3. Data

**Synthetic**, generated by `data_gen/` with controllable knobs (users, products, event rate, seasonality, persona distributions).

| Dataset | Grain | Key fields | Mode |
|---|---|---|---|
| `clickstream_events` | 1 row / event | event_id, user_id, session_id, event_type (view/add_to_cart/purchase/search), product_id, ts, device, referrer | Streaming (JSON files landing in a volume every N seconds) |
| `users` | 1 row / user | user_id, email, signup_ts, country, age_band, acquisition_channel, loyalty_tier | Batch + CDC updates |
| `products` | 1 row / SKU | product_id, title, description, category, brand, price, image_url, tags | Batch |
| `orders` | 1 row / order line | order_id, user_id, product_id, qty, unit_price, ts | Streaming |

The generator embeds *learnable* structure: user personas with category affinities, price sensitivity, session intent drift, and a cold-start cohort (~30% of sessions).

Medallion: **Bronze** raw + `_rescued_data` + ingestion metadata · **Silver** deduped, typed, PII-masked, sessionized events, SCD2 `users` · **Gold** `user_features`, `product_features`, `session_context`, `recommendation_log`, `recommendation_outcomes`, KPI tables.

## 4. Stage 1 — Lakeflow (Ingestion)

Lakeflow Declarative Pipelines in Python; Auto Loader on a UC Volume; AUTO CDC for `users`; streaming tables for bronze/silver; MVs for gold; expectations (`expect_or_drop` on null user_id/product_id, `expect` on ts bounds, price > 0) with a quarantine table; continuous mode for the demo window, triggered otherwise; Lakeflow Jobs chain generator → pipeline → feature refresh → weekly retrain → Lakebase sync.

**Acceptance:** new event visible in silver within < 1 min of landing; expectations dashboard shows drop rates.

## 5. Stage 2 — Unity Catalog (Governance)

Catalog `fevm_catalog_ra_test` with schemas `bronze`, `silver`, `gold`, `ml`, `app` (+ `serving` for Lakebase synced-table entries). PII: `email` tagged `pii=email`, column mask `mask_email()`, row filter by `country` for a regional analyst group. Tags `data_product`, `layer`, `sensitivity`. Groups `pers_engineers`, `pers_analysts`, app service principal. Feature tables with PKs; model `ml.recommender` with `@champion` / `@challenger`; volumes `raw_landing`, `model_artifacts`.

**Acceptance:** analyst querying silver sees masked emails; lineage graph shows app table ← model ← gold ← bronze.

## 6. Stage 3 — Lakebase (Operational Serving)

| Table | Source | Sync mode | Purpose |
|---|---|---|---|
| `user_features_online` | gold.user_features | Continuous synced table | Feature lookup at request time |
| `product_catalog` | gold.product_features | Triggered | Enrich recs with title/price/image |
| `precomputed_recs` | ml batch inference | Triggered (after retrain) | Fallback when model serving is slow/unavailable |
| `session_state` | app writes directly | Native Postgres | Last-N clicks for current session |
| `recommendation_log` | app writes directly | Native Postgres → exported to UC | Impression/click/purchase attribution |

**Latency target:** feature lookup + catalog join < 20 ms p95.

## 7. Stage 4 — ML + GenAI

Two-stage recommender: candidate generation (item-item CF via implicit ALS + Vector Search / gte-large semantic neighbours), LightGBM ranking on user + product + session-context features, MLflow + UC registration, Model Serving with champion/challenger, cold start via session items + segment popularity. Offline NDCG@10, Recall@50 on a temporal holdout. GenAI: grounded "why this?" explanations cached in Lakebase; merchandiser copilot with `ask_genie`, `simulate_campaign`, `lookup_product`; monitoring via inference tables.

## 8. Stage 5 — Genie Space

`Personalization Insights` over `recommendation_outcomes`, `session_kpis_daily`, `user_segments`, `product_performance`, `experiment_results`, with metric definitions, synonyms, trusted SQL and seeded sample questions; embedded in the app via the Conversation API.

## 9. Stage 6 — Databricks App

FastAPI backend (`/recs`, `/events`, `/kpis`, `/genie`, `/agent`, `/about`; async Lakebase pool with OAuth refresh; SDK for Serving / Genie; SSE for the agent) serving a React + Vite + TypeScript frontend with four pages: Storefront Simulator, Business Console, Ask the Data, About This Build.
